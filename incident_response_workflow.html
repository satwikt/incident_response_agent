Design walkthrough

Incident Response Agent that remembers

Logs are pushed in, the agent watches on its own, and every incident it handles is stored in Hindsight memory. The next time the same thing breaks, the agent recalls what fixed it and says so in the alert.

Who does what

The user does not have to type anything for the core flow. The agent is proactive; people react, approve and teach.

Default

Proactive

Logs stream in, the watcher spots a breach, and the agent recalls past incidents, diagnoses, and posts to Discord before anyone notices.

User enters: nothing. They receive an alert with the likely cause and a proposed fix.
On demand

Reactive chat

An engineer asks "why is /todos slow?". Same agent, same log tools, same memory recall, so answers get better over time.

User enters: a question, or a preference such as "keep answers short" or "never restart at peak". Preferences are retained.
The learning input

Feedback and approval

On the incident page the human approves or rejects the proposed fix, corrects the root cause, and marks the incident resolved.

User enters: clicks and a one-line correction. This is what turns a log into learning.

    How logs reach the agent

    Push over plain HTTP. No collector, no query language, no extra containers. Any app can use the same endpoint.

    App request or exception→ tiny log handler (batches, never blocks)→ POST /ingest/events→ SQLite events table→ agent tools (SQL) 
    POST /ingest/events
[
  {
    "ts": "2026-09-28T10:14:03Z",
    "service": "todo-app",
    "level": "ERROR",
    "route": "POST /todos",
    "status": 500,
    "duration_ms": 212,
    "message": "Unhandled ValueError in create_todo",
    "exception": "ValueError: injected failure"
  }
]
    -- what the tools compute from the same table
error_rate  = count(status>=500) / count(*)
              GROUP BY route, window
p95_latency = percentile(duration_ms, 0.95)
              GROUP BY route, window
recent_logs = WHERE message LIKE '%keyword%'
slowest     = ORDER BY duration_ms DESC LIMIT n
-- optional: file-tail adapter and a replay script
-- for seeding historical incidents

    Time to resolve, per incident

    Illustrative target for the demo storyline, not measured results. The real numbers come from the incident lifecycle (opened → resolved) once built.

    Demo storyline (about 3 minutes)

    1. Setup: Hindsight is pre-loaded with 30 to 50 realistic past incidents.
    2. Incident 1: inject a 500 storm on POST /todos. No close match, so the RCA is generic. The human approves a fix and the outcome is retained.
    3. Incident 2: inject the same fault. The alert says "recurrence of INC-1, this fix worked". One click approves it and resolution is much faster.
    4. Incident 3: inject a new latency fault. The agent recalls a similar but different seeded incident and adapts its advice.
    5. Close: show the Memory panel, the time-to-resolve trend and a reflected runbook. Repeat with memory off for the contrast.
